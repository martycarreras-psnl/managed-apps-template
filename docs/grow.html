Inventory

🗂️

Every environment belongs to a group

Admins set the rules once, for the whole group. Every environment in it, and every app pinned there, follows them automatically, including your personal developer environment.

🏛️

One place to govern it all

Other vibe-coding and low-code tools scatter governance across their own admin consoles. Here it's managed centrally in the Microsoft 365 admin center, with advanced controls in the Power Platform admin center.

The pin is permanent

An app can't move to another environment, and there's one copy of it, so every change you deploy is live for everyone right away. Running it somewhere else means registering a new app from the same code. That's exactly what the next sections set up.

2 of 4When to add rigor

Most apps need one.
Some need three.

If the app is just for you or a small team, keep it as it is. When it grows into something many people rely on, every change carries more risk, and that's the moment to give it a dev, a test and a prod version.

Keep it simple

Stay as you are when

  • it's just you, or a handful of people
  • a change going live right away is fine
  • if something breaks, you can fix it on the spot
Time to grow

Add dev, test and prod when

  • many people, or a whole team, depend on it
  • changes should be tried before users see them
  • you need to roll back a bad release in minutes
  • more than one person works on the code

3 of 4What you put in place

Four things.
That's the whole list.

Only your app's code moves between stages, so there's nothing else to package or keep in step. The template sets all four up for you.

1

Your own GitHub repo

Created from this template. It holds the code, every change's history, and the pull requests your team reviews.

2

Three apps, one codebase

A dev, a test and a prod app, each pinned to an environment your admins govern. Each is labeled [DEV], [TEST] or [PROD].

3

A branch per stage

dev, test and prod. Promoting is a merge, and each branch keeps its own app binding automatically.

4

Guarded deploys

Every deploy checks the branch, the binding and the build first. Roll back or hotfix production in minutes.

Check your connectors in every stage

Each environment has its own data policy, so a connector allowed in dev might be blocked in prod. Ask your agent "Can I use the Office 365 Outlook connector in test and prod?" before you promote.

Bringing your current app over

  1. Create your repo from this template.
  2. Bring your code in. Your agent copies it from your current app (ms app clone) into the new project.
  3. Register dev, test and prod, each pinned to an environment your admins govern. Ask them which ones to use.
  4. Share the prod app with your users. It has its own link. Your original app keeps running, so you can keep it as a personal sandbox or retire it.

↩

Roll back

A bad release? Redeploy the last good commit to prod, then fix forward. Say "Roll back production to the last good version."

🩹

Hotfix

Fix prod without shipping unfinished work: branch from prod, fix, land it, and the fix flows back to dev. Say "I need a hotfix in production."

The tooling refuses to ship a mistake

Wrong branch, uncommitted changes, an app bound to the wrong environment, or a build that fails: alm:deploy stops and tells you how to fix it. Nothing reaches users until every check passes.

When it breaks

Common snags and what they mean.

Or skip the reading and tell your agent "Help me fix this error."

A connector works in dev but is blocked in test or prod
Each environment has its own data policy. Ask "Why is this connector blocked, and which environment is my app pinned to?" An app can't change environments, so the fix is a policy change by your admins, or a different connector.
The first deploy fails with rejected (fetch first)
The app's platform repo starts with its own commit. Run npm run alm:bootstrap -- dev in a terminal you can see (it opens a one-time sign-in), then deploy again.
A promotion reports a conflict in ms.config.json
That file binds each branch to its own app. Keep the target branch's copy (git checkout --ours ms.config.json) and make sure npm run alm:setup has been run in this clone.
alm:deploy says I'm on the wrong branch
Each stage deploys only from its own branch. Run git checkout test (or prod) first, or just ask your agent to deploy.
