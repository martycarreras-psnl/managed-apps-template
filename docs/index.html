1 of 4How it works · start with what you know

Environments and solutions.
The model you already trust.

If you've built with Power Apps, you know this. An environment is a governed container with its own Dataverse, data policies, connections, security roles and admins. A solution carries your work between environments: build it unmanaged in dev, export it as a managed .zip, and import that same file into test and then prod.

Unmanaged in dev

You author tables, apps, flows and roles directly in the dev environment. Everything stays editable.

Managed downstream

Test and prod receive a managed solution. It's locked, versioned, and upgraded or removed as one unit.

Governed where it lives

Each environment applies its own data policies, connections and security roles to whatever is imported into it.

See it in motion

Sketch 1 is where most teams start: the environment is the source of truth, and a managed zip is the only thing that travels. Sketch 2 is where mature teams, usually backed by a Center of Excellence, end up: the solution unpacked into Git, then built and deployed by a pipeline.

Hold onto this picture

In classic Power Platform, the environment is two things at once: where the app lives and where it's governed. Managed Apps split those two apart. Solutions and Dataverse still work exactly as they do here.

2 of 4How it works · what's different

A separate runtime,
governed by its environment.

A Managed App doesn't live inside an environment the way a canvas app does. It's React code in git, built and served by one shared runtime. It is still governed by the environment it's pinned to. You choose that environment once, when the app is created. If you don't, it's pinned to your Personal Developer Environment (PDE).

Choose the environment on purpose

With no --environment-id, the app is pinned to your PDE and follows whatever rules your admins set for developer environments. That's fine for a personal app. For team or production apps, pin each stage to an environment your admins govern, so its policies apply. This template's alm:init always passes the environment ID.

Most apps need one. Some need three.

An app built for yourself or a small team doesn't need source control of its own or extra environments. When it grows into something many people rely on, changes need more care. That's when it graduates to a dev, a test and a prod app, each pinned to its own environment.

All three apps land in the same Apps list

"Dev", "test" and "prod" are not runtime concepts. Each is a separate app registration, and every one of them shows up in the same tenant-wide Apps list — with no environment column to tell them apart.

Name your apps per environment

Nothing in the admin surface tells you which environment an app belongs to. Use "Expense Tracker [DEV]", [TEST], [PROD] — or an admin cannot tell which of three identical rows is production.

So there are now two tracks

The app's code moves through git. Its Dataverse schema (tables, columns, security roles) still moves as a managed solution, just like before. A Managed App is not a solution component, so the solution can't carry the app, and git can't carry the tables. Keeping those two tracks in step across dev, test and prod is the hard part, and it isn't the only one. Here's what goes wrong.

3 of 4How it works · what goes wrong

Building the app is the easy part now.
Operating it is the hard part.

AI agents can scaffold a working app in minutes. Enterprises also need that app promoted safely, schema kept aligned, and every environment auditable. We hit each of these pitfalls for real and built the fix into this template. Tap a card to see the fix.

Pitfall

One merge rebinds prod to dev

ms.config.json pins an app to its environment. A normal merge copies dev's binding into prod.

Built in

A merge driver pins it per branch

Each branch keeps its own binding. alm:deploy refuses to deploy if the binding doesn't match its target.

Pitfall

The app ships, but its tables don't

The code promotes through git. The Dataverse schema stays behind in dev, so test breaks.

Built in

A managed solution travels with the code

The solution is exported as managed, committed with a SHA-256 manifest, merged with the code, then imported. Deploy is blocked if versions drift.

Pitfall

Three identical apps in the admin center

Dev, test, and prod share one runtime, each governed by its own environment, and show up in one flat list with no environment column.

Built in

Each environment is labeled

Each branch owns its display name: [DEV], [TEST], or [PROD]. Admins can see which app is which.

Pitfall

"It works for me" access

Users can open the app but get errors on data. Sharing the app and granting Dataverse access are two separate gates.

Built in

Least-privilege roles ship with the solution

Security roles live in the solution, and each connection declares its allowedActions. Both gates are documented and repeatable.

Pitfall

Hotfix while a feature is in flight

Prod is on fire and dev has half-built work. Where do you branch from?

Built in

A documented hotfix lane

Branch from prod, fix it, then merge back down so every environment gets the fix and none of the unfinished work.

Pitfall

Every team rebuilds the pipeline

Fifty projects end up with fifty slightly different versions of the scripts, all drifting apart.

Built in

A versioned upgrade channel

Scaffolding is tagged scaffold-vX.Y.Z. Any project can run npm run alm:upgrade to get the latest fixes.

4 of 4How it works · putting it together

One branch per environment.
Everything moves together.

Each stage is its own app, pinned to its own environment. Each branch carries the app code and the managed solution side by side, so promotion is a git merge. Every app is served by the one shared Managed Apps runtime, but each is pinned to, and governed by, its own environment: that environment's policies, connections, and Dataverse.

🔀 Promote = merge

npm run alm:promote test. The PR is the approval, and branch protection enforces it.

📦 Schema rides along

The managed solution is exported from dev, committed to solutions/, and imported downstream.

🧷 Guarded deploys

Environment binding, solution version, and clean-tree checks run before every alm:deploy.

🪞 Remotes in sync

Hooks mirror each branch to its environment's platform git repo, so the runtime always builds the code you reviewed.

The one change from the classic flow: nothing moves environment-to-environment

In the classic flow the zip went straight from dev to test. Here it doesn't. The managed solution leaves dev as a file, lands in solutions/, and travels as a git artifact. Test and prod are only ever written to by an import from a branch.

1 · Export into the repo

alm:solution export pulls the managed solution out of dev and commits it to solutions/ with a version and checksum.

2 · Promote the branch

alm:promote merges dev into test. The same commit now carries the same code and the same solution zip.

3 · Import from the branch

alm:solution import test pushes that artifact into the target's Dataverse. Then the app deploys — and only then.

Connect to anything

Your data is probably already here.
So are your guardrails.

Managed Apps use the Power Platform connector catalog: 1,300+ connectors from Microsoft 365 and Dataverse to SAP, Salesforce, ServiceNow, SQL, and Snowflake, plus any custom connector your team publishes. You ask for data in plain language, and the agent wires up typed services.

🛡️

Governed by the controls you already run. Every app is pinned to a Power Platform environment (your personal developer environment unless you choose one) and follows its DLP policies, connector allow/block lists, and security, with Entra identity on top. Makers move fast inside the lines IT has already drawn.

💬

Ask in plain language

"Add a SharePoint list of vendors and let me email them from Outlook." The agent's skills pick the connector and generate typed TypeScript services.

🔐

Least privilege by default

Each shared connection declares exactly which actions the app may call. Deploy fails closed if a declaration is missing.

🗄️

Dataverse when you need it

Need real tables, relationships, and roles? Dataverse skills create the schema, and the solution pipeline carries it to every environment.

Will this connector work in my environments?

Start with Microsoft's up-to-date catalogs, the list of connectors and the list of MCP servers. Being listed doesn't mean you can use it. Your organization's data policy decides that for each environment separately. 

ms connector list -e <env-id> --search outlook                          # Policy Status: Allowed / Blocked
ms connector list-actions --connector office365 -e <env-id> --search send  # which actions are allowed

Always name the environment and check each one

Without -e the CLI checks your personal developer environment instead. A connector allowed in dev can still be blocked in prod. Or just ask your agent: "Can I use the Office 365 Outlook connector in test and prod?"

If a connector is blocked, your agent stops and tells you

An app is pinned to the environment it was registered in, and that pin can't change. When a connector or MCP server is blocked there, the devkit stops before adding it or writing code for it. It tells you which connector is blocked, which environment your app is pinned to, and whether it's allowed in each of your other stages. That includes any stage you add later, like QA or UAT, because it reads them from alm.config.json. Your choices are to ask your Power Platform admin to allow it in the data policy, or to pick an allowed alternative. The agent never works around it.

cd <your-repo>

alm:init also records dev's Dataverse URL, and removes ms.config.json and solutions/ from .gitignore: the template ignores them, but your project must commit both. With --fresh it leaves a placeholder page that builds.

Why alm:setup is not optional

It registers the git merge driver that pins ms.config.json to each branch. Without it, promoting dev → prod overwrites production's binding with dev's and repoints your live app at the sandbox Dataverse.

Ship it

Two things travel together.
The tooling won't let them split.

App code moves as a git commit. Schema moves as a managed solution committed into that same commit. Deploying one without the other is the most common way to break an environment, so alm:deploy refuses. Here's one change, from your laptop to test. Sketch 5 shows it in motion.

Walk through a change

git checkout -b feature/thing dev
ms app dev                       # local, hot reload
git commit -am "feat: thing"
git push -u github feature/thing  # open a PR into dev, merge after CI
git checkout dev && git pull github dev
npm run alm:deploy -- dev

Dev is the only environment where schema is authored. Everywhere else it arrives as managed.

npm run alm:solution -- export -- --bump build

✓ version 1.0.1.0 -> 1.0.2.0
✓ InventoryApp_managed.zip (11662 bytes)
✓ manifest v1.0.2.0

The zip and a sha256 manifest are committed to solutions/, so the artifact is reviewable and verifiable.

npm run alm:promote -- test

✓ merge driver registered
✓ checked out test
✓ ms.config.json unchanged — environment binding intact

Only code moves. Test keeps its own ms.config.json, so it still points at the test app.

npm run alm:deploy -- test

✓ connection references match this environment
✗ Schema drift: test has v1.0.1.0 but the repo ships v1.0.2.0.
  Run: npm run alm:solution -- import test

Blocked before anything is pushed. The app would have called columns that do not exist yet.

npm run alm:solution -- import test
✓ artifact verified (sha256 76ae0480f3d1…)
✓ installed v1.0.2.0 (managed: true)

npm run alm:deploy -- test
✓ solution v1.0.2.0 in lockstep with test
✓ Deployed test

Repeat for prod. Schema first, always — ms app add data-source reads table metadata from the target org.

Dataverse solutions do not branch

Git gives you hotfix/x off prod; your dev environment has no equivalent — it holds whatever schema you have been building. So a hotfix needing a schema change cannot cleanly export from dev. Keep schema additive and decoupled from app releases, and this never bites.

Give people access

Two independent gates.
Open the app, then see the data.

Sharing an app does not grant access to its data. They are separate systems, and as an administrator you won't notice the gap, because you pass both gates automatically.

Why you will not catch this yourself

As a System Administrator you implicitly hold every privilege, so both gates pass silently. Test with a real non-admin account before shipping. 

npm run alm:role -- create   # role travels in the managed solution
npm run alm:role -- show     # verify across all environments

When it breaks

Real failures
and what they mean.

Every entry here actually happened. Or skip the reading and tell your agent “Help me fix this error”: the devkit knows all of these. Commands for

Git Credential Manager is installed but not configured

GCM exists but is not registered as a credential helper, so ms app create fails preflight. Run git credential-manager configure. Common on macOS; Git for Windows does this for you.

The first deploy or bootstrap hangs with no output

The first fetch from the app's platform repo opens a Git Credential Manager sign-in. In an agent's shell that prompt is hidden, so the command waits forever. Stop it and run npm run alm:bootstrap -- dev in a terminal you can see, finish the sign-in, then carry on. It only happens once per machine.

The App Player is blank or won't sign in

Agent side-panel browsers can't run the App Player. Open the link from ms app dev in Chrome or Edge instead.

CI: "ms.config.json keeps the target branch's binding" fails

Pull requests into dev may change ms.config.json (adding a data source writes to it), but it must still point at dev's app and environment. Pull requests into test or prod must not change it at all. If it failed, the branch carries another environment's binding: restore the file from the target branch.

alm:solution or alm:role: "no dataverseUrl"

The scripts reach Dataverse by URL. Run alm:init again while signed in to the Dataverse CLI or pac, or copy the URL from dataverse org list --json --filter <env-id> into alm.config.json → environments.dev.dataverseUrl.

'.' is not empty. Specify an empty directory

ms app create counts .git as content, so it refuses an existing repo. Use ms app init instead — which is what alm:init does.

The Microsoft GitHub App can't access the bound repository

The Microsoft GitHub App is not installed on the owning account, and enterprise-managed (EMU) accounts usually cannot install third-party GitHub Apps. Use --repo native — a platform-managed repo — which this template does by default.

External artifact deployment is not enabled for this environment

The app was registered with repoType: "none", which uploads a local zip and requires the AllowExternalArtifactDeployment environment setting. That setting is off by default and is not settable from any CLI — it is not a Dataverse organization column, not in settingdefinition, and not in pac admin list-tenant-settings. Re-register with --repo native to use the cloud build path instead.

! [rejected] … (fetch first) on the first push to a platform repo

A newly provisioned platform repo ships its own unrelated "Initial commit", so the first push is a non-fast-forward. Run npm run alm:bootstrap -- <env>, which joins the histories and resolves the stub README in your favour.

fatal: Cannot prompt because user interactivity has been disabled

Some agent harnesses set GIT_TERMINAL_PROMPT=0 and GCM_INTERACTIVE=Never. The ALM scripts override this automatically. For a manual push:

GIT_TERMINAL_PROMPT=1 GCM_INTERACTIVE=1 GCM_GUI_PROMPT=0 git push origin HEAD
$env:GIT_TERMINAL_PROMPT="1"; $env:GCM_INTERACTIVE="1"; git push origin HEAD
A connector is "policy-blocked" / Policy Status: Blocked

The data (DLP) policy of the environment your app is pinned to blocks that connector. You'll see this for Work IQ, for example, when every Work IQ connector is blocked. Apps can't move environments, so there's no setting on your side that fixes it. Run node .github/skills/managed-apps-devkit/scripts/connector-check.mjs <name> to see where it's allowed. It shows one column for every stage in alm.config.json. Then ask your Power Platform admin to allow it in the data policy, or use a connector that's already allowed. If the app is pinned to your personal developer environment, it was registered without --environment-id. Register the project against a governed environment instead. Or ask your agent: “Why is this connector blocked?”

Users can open the app but see an error on first load

Gate 2. They have app access but no Dataverse privileges on the table. Run npm run alm:role -- create and assign the role.

Playwright tests cannot sign in

Tenants enforcing passkey/FIDO cannot authenticate inside an automated browser — Chrome disables the platform authenticator under automation, so the Touch ID / Windows Hello prompt never appears. Use an account with password or Authenticator sign-in.

merge conflict in ms.config.json during promotion

The merge driver is not registered in this clone — .gitattributes is committed, but the driver it references is local config. Run npm run alm:setup. Always keep the target branch's copy.
