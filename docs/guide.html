01 — The shape of it

The branch carries everything

The schema is not pushed from one environment to the next. It is exported out of dev into the repo, committed alongside the code, and then imported from each branch into that environment's Dataverse. One git merge promotes both — which is exactly why they cannot drift apart.

Nothing moves environment-to-environment

There is no direct dev → test path in Dataverse. The managed solution leaves dev as a file, lands in solutions/, and travels as a git artifact. Test and prod are only ever written to by an import from a branch.

And the app itself never enters an environment at all

The app record and its git repo are environment-scoped — the repo URL literally embeds the environment ID. But the built app is served from play.managedapps.cloud.microsoft, not from the environment. Deploying places nothing inside Dataverse.

1 · Export into the repo

alm:solution export pulls the managed solution out of dev and commits it to solutions/ with a version and checksum.

2 · Promote the branch

alm:promote merges dev into test. The same commit now carries the same code and the same solution zip.

3 · Import from the branch

alm:solution import test pushes that artifact into the target's Dataverse. Then the app deploys — and only then.

02 — The part that surprises people

All three apps land in the same place

"Dev", "test" and "prod" are not runtime concepts. Each is a separate app registration, and every one of them shows up in the same tenant-wide Apps list — with no environment column to tell them apart.

Name your apps per environment

Nothing in the admin surface tells you which environment an app belongs to. Use "Expense Tracker [DEV]", [TEST], [PROD] — or an admin cannot tell which of three identical rows is production.

03 — Getting started

Set up your machine

Pick your agent. The OS toggle in the nav switches the commands below.

Prerequisites

# macOS
brew install node git
brew install --cask git-credential-manager
git credential-manager configure   # REQUIRED — do not skip

npm install -g @microsoft/managed-apps-cli@latest
ms auth login
# Windows PowerShell — Git for Windows bundles and configures GCM
winget install OpenJS.NodeJS.LTS
winget install Git.Git

npm install -g '@microsoft/managed-apps-cli@latest'
ms auth login

The #1 first-run failure on macOS

Git Credential Manager can be installed but not registered as a credential helper, and ms app create fails preflight. git credential-manager configure fixes it. URL-scoped helpers such as GitHub's are unaffected.

Install the agent plugin

# run `copilot` in any folder, then:
/plugin marketplace add microsoft/Managed-Apps
/plugin install microsoft-managed-apps@Managed-Apps
# run `claude`, then — identical commands:
/plugin marketplace add microsoft/Managed-Apps
/plugin install microsoft-managed-apps@Managed-Apps

The desktop app runs Copilot CLI underneath and shares the same ~/.copilot configuration, so anything installed in either is available in both. Use the same slash commands in chat.

Create the project

# Use this template → Create a new repository, then:
git clone https://github.com/<you>/<your-repo>
cd <your-repo>
npm install
npm run alm:setup        # merge driver + hooks — REQUIRED, once per clone

npm run alm:init -- --name "Expense Tracker" --dev <dev-env-id> --prefix contoso

Why alm:setup is not optional

It registers the git merge driver that pins ms.config.json to each branch. Without it, promoting dev → prod overwrites production's binding with dev's and repoints your live app at the sandbox Dataverse.

04 — Moving changes

Two things travel together

App code moves as a git commit. Schema moves as a managed solution committed into that same commit. Deploying one without the other is the most common way to break an environment — so the tooling refuses to let you.

Walk through a change

git checkout -b feature/thing dev
ms app dev                       # local, hot reload
git commit -am "feat: thing"
git checkout dev && git merge feature/thing
npm run alm:deploy -- dev

Dev is the only environment where schema is authored. Everywhere else it arrives as managed.

npm run alm:solution -- export -- --bump build

✓ version 1.0.1.0 -> 1.0.2.0
✓ CopilotAppsFoundations_managed.zip (11662 bytes)
✓ manifest v1.0.2.0

The zip and a sha256 manifest are committed to solutions/, so the artifact is reviewable and verifiable.

npm run alm:promote -- test

✓ merge driver registered
✓ checked out test
✓ ms.config.json unchanged — environment binding intact

Only code moves. Test keeps its own ms.config.json, so it still points at the test app.

npm run alm:deploy -- test

✓ connection references match this environment
✗ Schema drift: test has v1.0.1.0 but the repo ships v1.0.2.0.
  Run: npm run alm:solution -- import test

Blocked before anything is pushed. The app would have called columns that do not exist yet.

npm run alm:solution -- import test
✓ artifact verified (sha256 76ae0480f3d1…)
✓ installed v1.0.2.0 (managed: true)

npm run alm:deploy -- test
✓ solution v1.0.2.0 in lockstep with test
✓ Deployed test

Repeat for prod. Schema first, always — ms app add data-source reads table metadata from the target org.

Dataverse solutions do not branch

Git gives you hotfix/x off prod; your dev environment has no equivalent — it holds whatever schema you have been building. So a hotfix needing a schema change cannot cleanly export from dev. Keep schema additive and decoupled from app releases, and this never bites.

05 — Who can actually use it

Two independent gates

Sharing an app does not grant access to its data. These are separate systems, and you will not notice as an administrator.

Why you will not catch this yourself

As a System Administrator you implicitly hold every privilege, so both gates pass silently. Test with a real non-admin account before shipping. 

npm run alm:role -- create   # role travels in the managed solution
npm run alm:role -- show     # verify across all environments

06 — When it breaks

Real failures and what they mean

Every entry here is something that actually happened, not a hypothetical.

Git Credential Manager is installed but not configured

GCM exists but is not registered as a credential helper, so ms app create fails preflight. Run git credential-manager configure. Common on macOS; Git for Windows does this for you.

'.' is not empty. Specify an empty directory

ms app create counts .git as content, so it refuses an existing repo. Use ms app init instead — which is what alm:init does.

The Microsoft GitHub App can't access the bound repository

The Microsoft GitHub App is not installed on the owning account, and enterprise-managed (EMU) accounts usually cannot install third-party GitHub Apps. Use --repo native — a platform-managed repo — which this template does by default.

External artifact deployment is not enabled for this environment

The app was registered with repoType: "none", which uploads a local zip and requires the AllowExternalArtifactDeployment environment setting. That setting is off by default and is not settable from any CLI — it is not a Dataverse organization column, not in settingdefinition, and not in pac admin list-tenant-settings. Re-register with --repo native to use the cloud build path instead.

! [rejected] … (fetch first) on the first push to a platform repo

A newly provisioned platform repo ships its own unrelated "Initial commit", so the first push is a non-fast-forward. Run npm run alm:bootstrap -- <env>, which joins the histories and resolves the stub README in your favour.

fatal: Cannot prompt because user interactivity has been disabled

Some agent harnesses set GIT_TERMINAL_PROMPT=0 and GCM_INTERACTIVE=Never. The ALM scripts override this automatically. For a manual push:

GIT_TERMINAL_PROMPT=1 GCM_INTERACTIVE=1 GCM_GUI_PROMPT=0 git push origin HEAD
$env:GIT_TERMINAL_PROMPT="1"; $env:GCM_INTERACTIVE="1"; git push origin HEAD
Users can open the app but see an error on first load

Gate 2. They have app access but no Dataverse privileges on the table. Run npm run alm:role -- create and assign the role.

Playwright tests cannot sign in

Tenants enforcing passkey/FIDO cannot authenticate inside an automated browser — Chrome disables the platform authenticator under automation, so the Touch ID / Windows Hello prompt never appears. Use an account with password or Authenticator sign-in.

merge conflict in ms.config.json during promotion

The merge driver is not registered in this clone — .gitattributes is committed, but the driver it references is local config. Run npm run alm:setup. Always keep the target branch's copy.
